# Week 09 Lab - Answers to Questions

### Question 1 (Part 0)
* **`public` schema:** It is not a database. A database is the highest-level independent storage container, while `public` is a default schema (namespace) inside the database used to organize and group tables.

### Question 2 (Part 1)
* **`SERIAL` behind the scenes:** It creates an underlying sequence object, sets the column type to `INTEGER`, and assigns a default value using `nextval(...)` to auto-increment the ID upon record insertion.

### Question 3 (Part 1)
* **Dropping a referenced table:** PostgreSQL raises a foreign key constraint violation.
* **Resolution:** Drop the child table (`hero`) before the parent table (`team`), or run `DROP TABLE team CASCADE;`.

### Question 4 (Part 2)
* **Reason 1 (Security):** Prevents hardcoded database credentials from being leaked to version control systems like Git.
* **Reason 2 (Flexibility):** Allows seamless configuration switching across different environments (Development, Testing, Staging, Production) without modifying source code.

### Question 5 (Part 3)
* **Difference:** `Hero` is a table model representing the database schema and contains sensitive fields like `secret_name`. `HeroPublic` is a response schema returned via the API that omits `secret_name`.
* **Purpose:** Ensures data hiding and security by preventing sensitive hero identities from being exposed through public API endpoints.

### Question 6 (Part 3)
* **`Hero.id` as `int | None = None`:** When an object is instantiated in Python before being saved, it has no ID yet. In PostgreSQL, the column is `NOT NULL` because the database automatically generates and assigns an auto-incrementing integer primary key upon insertion.

### Question 7 (Part 4)
* **Comparison:** SQLModel generates standard SQL using `INTEGER GENERATED BY DEFAULT AS IDENTITY` (or `SERIAL`), defines explicit `VARCHAR` types, sets explicit `NOT NULL` and `PRIMARY KEY` constraints, and automatically issues separate `CREATE INDEX` statements for indexed fields.

### Question 8 (Part 4)
* **`create_all` on restart:** It does not re-run `CREATE TABLE`. `create_all` checks the database's system catalog first; because the tables already exist, it skips them.

### Question 9 (Part 4)
* **Metadata registration line:** `from app import models` (or direct model imports). Removing this line leaves SQLModel's metadata empty, causing `create_all` to execute without creating any tables in the database.

### Question 10 (Part 5)
* **Omitting `session.commit()`:** The hero is not saved to the database because changes remain only in the session staging area.
* **`session.refresh(hero)`:** Queries the database to reload the latest state of the object, updating database-generated attributes such as the auto-incremented `id`.

### Question 11 (Part 5)
* **Using `exclude_unset=False`:** Fields omitted by the client default to `None`. As a result, columns such as `name`, `secret_name`, and `team_id` would be overwritten with `None` (or trigger database constraint violations), rather than updating only the provided `age` field.

### Question 12 (Part 5)
* **Presence of `secret_name`:** No. Because the endpoint defines `response_model=HeroPublic`, FastAPI serializes only the attributes specified in `HeroPublic`, automatically excluding `secret_name`.

### Question 13 (Part 6)
* **Parameter placement:** The values appear as parameterized placeholders (such as `%(age_1)s`, `$1`) rather than raw concatenated strings.
* **Security:** Separating query structure from input data ensures the database parses the SQL statement before applying parameter values, preventing SQL injection attacks.

### Question 14 (Part 6)
* **Reason 1:** Avoids loading large datasets across the network into application RAM, preventing high bandwidth consumption and memory exhaustion.
* **Reason 2:** Leverages database indexes and query optimization engines to execute searches significantly faster than sequential in-memory Python filtering.

### Question 15 (Part 7)
* **Behavior:** `create_all` inspects each table individually. The `hero` table is skipped because it already exists, while `mission` and `heromissionlink` are newly declared and missing from the database, prompting `CREATE TABLE` executions for them.

### Question 16 (Part 8)
* **Execution order:** `team` records are inserted first, followed by `hero` records, and finally `heromissionlink` records.
* **Resolving `team_id`:** Using the ORM relationship `team=t1`, SQLAlchemy evaluates dependencies, retrieves the generated primary key `id` after inserting the team, and assigns it to the hero's `team_id` foreign key before executing the hero insert.

### Question 17 (Part 9)
* **Production unsuitability:** Dropping tables permanently destroys active customer records and production state. Migrations modify existing schemas (such as adding or modifying columns) while preserving existing data.

### Question 18 (Part 9)
* **`upgrade()`:** Contains DDL operations (such as `op.add_column`) to apply new schema changes, specifically adding the `power` column to `hero`.
* **`downgrade()`:** Contains operations that reverse the upgrade (such as `op.drop_column`) to enable rollbacks.

### Question 19 (Part 9)
* **Revision storage:** Stored in the `alembic_version` table inside the database.
* **Committing `migrations/`:** Ensures development teams, CI/CD pipelines, and production environments share an identical, version-controlled database schema history.

### Question 20 (Part 9)
* **Outcome:** The migration fails with an error (`relation "hero" does not exist`).
* **Explanation:** The generated migration contains only an `op.add_column` operation for `hero.power`, assuming baseline tables already exist. Running it against an empty database that never executed initial table creation fails because the target table does not exist.
